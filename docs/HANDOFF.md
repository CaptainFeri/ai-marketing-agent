# Handoff — پلتفرم تولید محتوای SEO/GEO و چندرسانه‌ای

> وضعیت: **طراحی تمام شده، پیاده‌سازی شروع نشده.**
> تاریخ: ۲۹ شهریور ۱۴۰۵ (2026-09-20)
> این فایل خلاصه تصمیم‌ها و برنامه کامل فازهاست. هر جا با سند معماری تناقض داشت، سند معماری معتبر است.

## ۱. پروژه در یک پاراگراف

یک پلتفرم **SaaS چندمشتری** که خط تولید محتوای هفت‌مرحله‌ای را اجرا می‌کند:
- پرسشنامه برند را می‌شناسد.
- زنجیره‌ای از ایجنت‌ها متن SEO/GEO می‌نویسند.
- متن برای هر کانال بازاریابی‌محور می‌شود.
- بعد از **تایید انسانی** تصویر و ویدیو به‌صورت موازی تولید می‌شوند.
- **انسان** گزینه‌ها را انتخاب و زمان‌بندی می‌کند.
- محتوا منتشر می‌شود و عملکرد و رشد اندازه‌گیری و به چرخه بعد برگردانده می‌شود.

همه مدل‌ها روی یک **RTX 3090 Ti** (۲۴ گیگ VRAM) اجرا می‌شوند.

## ۲. تصمیم‌های قطعی

| # | تصمیم | توضیح |
|---|---|---|
| D1 | همه مدل‌ها **خودمیزبان** | هیچ فراخوانی به API مدل‌های خارجی نداریم و داده از سرور خارج نمی‌شود |
| D2 | **MVP بدون هزینه اشتراک/API** | گزینه‌های پولی فقط در فاز ۴ (بهبود) می‌آیند |
| D3 | زبان‌ها: **فارسی، انگلیسی، عربی** | متن، صدا و زیرنویس. کیورد هر زبان جدا تحقیق می‌شود (بومی‌سازی، نه ترجمه) |
| D4 | ویدیو **سه حالت** دارد: `face` / `voice` / `none` | پیش‌فرض در Brand Brief تعیین می‌شود و ویراستار برای هر بسته می‌تواند عوضش کند |
| D5 | ارکستراسیون: **Celery + Redis** | Temporal در فاز ۴ |

| D7 | چهره و صدای واقعی فقط با **رضایت‌نامه کتبی** | خروجی آواتار برچسب «ساخته‌شده با AI» می‌گیرد |
| D8 | **چندمشتری (Multi-tenant)** | از روز اول `tenant_id` در همه جدول‌ها وجود دارد و داده، فایل و اعتبارنامه‌های کانال هر مشتری ایزوله است |
| D9 | سخت‌افزار: **یک RTX 3090 Ti با ۲۴ گیگ حافظه** | مدل‌ها روی GPU نوبتی اجرا می‌شوند (بخش ۶) |
| D10 | **حجم تولید تابع ظرفیت** است | سیستم زمان GPU هر مرحله را اندازه می‌گیرد و سهمیه روزانه هر مشتری را از ظرفیت واقعی حساب می‌کند (بخش ۷) |

## ۳. جریان کار

```
۱ پرسشنامه → Brand Brief (JSON)
۲ پایپلاین متن: پژوهشگر → استراتژیست → نویسنده → بهینه‌ساز GEO → بهینه‌ساز SEO → QA
      (اگر QA امتیاز کم بدهد، حداکثر ۲ بار به نویسنده برمی‌گردد و بعد به انسان ارجاع می‌شود)
۳ بازاریابی‌سازی → نسخه هر کانال + visual_brief + نسخه‌های A/B
   ── دروازه انسانی ۱: تایید / بازگشت با بازخورد / رد ──
۴ تولید رسانه: صف تصویر ‖ صف ویدیو (روی یک GPU به‌صورت نوبتی)
   ── دروازه انسانی ۲: انتخاب گزینه + زمان‌بندی روی تقویم (شمسی/میلادی) ──
۶ انتشار: Scheduler → کانکتور هر کانال (سه بار تلاش مجدد، سپس هشدار به اپراتور)
۷ سنجش: آمار روزانه → داشبورد → حلقه بازخورد (Refresh برای رتبه ۸ تا ۲۰)
```

چرخه وضعیت ContentPackage:
`Planned → Drafting → TextReview → (Drafting | Rejected | MediaGenerating) → Selection → Scheduled → Published → Measuring → (Refresh → Drafting)`

## ۵. مدل‌ها (برای ۲۴ گیگ VRAM؛ در فاز ۰ آزموده شوند)

| کار | مدل | مجوز | VRAM تقریبی | محل اجرا |
|---|---|---|---|---|
| متن fa/en/ar | **Qwen3-30B-A3B** (MoE، کوانتایز ۴بیتی). جایگزین: Qwen3-14B یا Gemma 3 12B | Apache-2.0 / Gemma Terms | ~۱۸ گیگ | GPU (vLLM) |

| TTS فارسی | Piper (صداهای fa_IR) | مجوز هر صدا جدا بررسی شود | — | **CPU** |
| TTS انگلیسی/عربی | Chatterbox Multilingual | MIT | کم | GPU یا CPU |
| زیرنویس | Whisper large-v3 (faster-whisper) | MIT | ~۴ تا ۶ گیگ | GPU |

نکته‌ها:
- Chatterbox فارسی ندارد، پس مسیر صدای فارسی جداست.
- مدل‌های تصویر حروف فارسی و عربی را خراب می‌کنند. تصویر **بدون متن** ساخته می‌شود و متن با قالب HTML (Playwright) رویش رندر می‌شود.
- وزن مدل‌ها در یک مخزن داخلی با نسخه و مجوز نگهداری می‌شوند (آینه داخلی).
- حداقل **۶۴ گیگ RAM** سیستم لازم است (بهتر است ۱۲۸ گیگ باشد) تا بتوان وزن‌ها را موقتاً از GPU به RAM منتقل کرد. **NVMe** سرعت بارگذاری را بالا می‌برد.

## ۶. اجرای نوبتی روی یک GPU

LLM و مدل‌های رسانه‌ای هم‌زمان در ۲۴ گیگ جا نمی‌شوند. به همین دلیل یک **GPU Scheduler** مالک کارت است:

- **دو پنجره کاری:** «پنجره متن» (LLM بارگذاری‌شده) و «پنجره رسانه» (تصویر، ویدیو، صدا، لب‌خوانی). Scheduler بر اساس صف منتظر و با کمترین تعویض بین این دو جابه‌جا می‌شود.
- **تعویض LLM:** از حالت sleep در vLLM استفاده می‌شود تا وزن‌ها به RAM بروند و سریع برگردند. اگر پایدار نبود، vLLM متوقف و دوباره اجرا می‌شود. زمان تعویض در فاز ۰ اندازه‌گیری می‌شود.
- **دسته‌بندی کارها:** کارهای هم‌نوع با هم اجرا می‌شوند. مثلاً همه تصاویر منتظر، پشت سر هم با یک بار بارگذاری FLUX.
- **صف منصفانه بین مشتری‌ها:** نوبت‌دهی چرخشی (round-robin) با وزن پلن مشتری، تا یک مشتری کل GPU را اشغال نکند.
- **کارهای شبانه:** ویدیوهای سنگین (کلیپ Wan و `face`) در بازه کم‌ترافیک اجرا می‌شوند.

## ۷. ظرفیت و سهمیه (حجم تابع توانایی)

اعداد زیر **تخمین اولیه** برای 3090 Ti هستند و فقط برای برنامه‌ریزی آمده‌اند. عدد واقعی در فاز ۰ اندازه‌گیری و در سیستم ثبت می‌شود.

| کار | زمان GPU تخمینی |
|---|---|
| یک بسته متنی کامل (۶ ایجنت + بازاریابی‌سازی، یک زبان) | ۵ تا ۱۰ دقیقه |
| یک تصویر 1024px با FLUX-schnell | ۵ تا ۱۵ ثانیه |
| ویدیوی ۶۰ ثانیه‌ای حالت `voice` یا `none` (بدون کلیپ AI) | ۱ تا ۳ دقیقه |
| یک کلیپ ۵ ثانیه‌ای 720p با Wan 2.2 5B | ۱۰ تا ۱۵ دقیقه |
| ۶۰ ثانیه لب‌خوانی با LatentSync | ۵ تا ۱۰ دقیقه |

برداشت تقریبی: در ۲۰ ساعت کار روزانه GPU، حدود **۱۵ تا ۳۰ بسته کامل در روز** با ویدیوی `voice` و تصویر ساخته می‌شود. هر کلیپ Wan یا ویدیوی `face` این عدد را به‌طور محسوس کم می‌کند.

**مکانیزم سهمیه:**
1. هر مرحله زمان واقعی GPU خود را در `StepRun.gpu_seconds` ثبت می‌کند.
2. «هزینه» هر نوع بسته بر اساس میانگین متحرک این زمان‌ها حساب می‌شود.
3. ظرفیت روزانه (ثانیه GPU) بین مشتری‌ها بر اساس وزن پلن تقسیم می‌شود.
4. پنل به هر مشتری نشان می‌دهد با سهمیه امروز چند بسته از هر نوع می‌تواند بسازد. درخواست بیش از سهمیه به روز بعد می‌رود.
5. با اضافه شدن GPU در فاز ۴، ظرفیت خودکار بالا می‌رود.

## ۸. حالت‌های ویدیو

| `video_mode` | زنجیره | هزینه GPU |
|---|---|---|
| `none` | تصویر/کلیپ → متن روی تصویر → موسیقی → FFmpeg | کم |
| `voice` | TTS → Whisper (زمان‌بندی زیرنویس) → تصاویر/کلیپ‌ها → FFmpeg | کم |
| `face` | TTS یا صدای ضبط‌شده → لب‌خوانی روی عکس (SadTalker) یا ویدیوی مرجع ۳۰ تا ۶۰ ثانیه‌ای (LatentSync) → FFmpeg | بالا |

# ۱۱. برنامه کامل فازها

مدت‌ها برای تیم ۲ تا ۳ نفره تخمین زده شده‌اند. هر فاز فقط وقتی تمام است که **معیارهای پذیرش** آن برقرار باشد.

## فاز ۰ — اعتبارسنجی فنی (۲ هفته)

**هدف:** قبل از ساختن محصول ثابت شود که کیفیت مدل‌ها در سه زبان قابل قبول است و 3090 Ti بار کار را تحمل می‌کند.

**کارها:**
- [ ] نصب درایور، CUDA و Docker روی سرور و راه‌اندازی MinIO، Postgres و Redis
- [ ] اجرای vLLM با Qwen3-30B-A3B (۴بیتی) و Qwen3-14B و مقایسه آن‌ها با ۵ پرامپت نمونه در هر زبان
- [ ] آزمون حالت sleep در vLLM و اندازه‌گیری زمان تعویض LLM ↔ FLUX
- [ ] نوشتن JSON Schema خروجی شش ایجنت متن و ایجنت بازاریابی
- [ ] اسکریپت پایپلاین متن از Brief تا `article.json` و تولید ۱۰ مقاله آزمایشی (fa/en/ar)
- [ ] راه‌اندازی FLUX.1-schnell روی ComfyUI و ساخت یک قالب HTML برای متن فارسی/عربی روی تصویر
- [ ] نمونه صدای Piper فارسی و Chatterbox انگلیسی/عربی و یک ویدیوی `voice` با FFmpeg
- [ ] آزمون Wan 2.2 5B و LatentSync روی 3090 Ti و ثبت زمان، VRAM و کیفیت
- [ ] پر کردن جدول زمان GPU بخش ۷ با اعداد واقعی
- [ ] پر کردن یک Brand Brief واقعی

**معیار پذیرش:**
- دست‌کم ۷ مقاله از ۱۰ مقاله هر زبان به داوری ویراستار «قابل انتشار با ویرایش جزئی» باشند
- کل زنجیره (متن + تصویر + ویدیوی `voice`) برای یک بسته بدون خطای حافظه (OOM) اجرا شود
- مدل‌های نهایی انتخاب و در مخزن داخلی ثبت شده باشند

**خروجی:** گزارش مقایسه مدل‌ها، جدول ظرفیت واقعی، اسکریپت‌های پایپلاین.

## ۱۳. ریسک‌های اصلی

- **یک GPU گلوگاه همه چیز است** ← Scheduler، کارهای شبانه، سهمیه، GPU دوم در فاز ۴
- **تأمین GPU و دسترسی به وزن مدل‌ها و API کانال‌ها از ایران** ← آینه داخلی و جدا کردن سرویس انتشار از سرور مدل‌ها
- **نشت داده بین مشتری‌ها** ← RLS، آزمون خودکار ایزوله‌سازی، رمزنگاری اعتبارنامه‌ها
- **محتوای انبوه و کم‌ارزش** ← دروازه انسانی، سقف تعداد انتشار، تزریق تجربه و داده اختصاصی برند
- **ادعاهای نادرست** ← برای هر آمار منبع لازم است و QA بررسی‌اش می‌کند
- **سوءاستفاده از چهره یا صدا** ← رضایت‌نامه، برچسب AI، دسترسی محدود
- **کیفیت TTS فارسی** ← مسیر جدا و فاین‌تیون در فاز ۴
